# humans.md — issues-to-roadmap

## Origin

Written from pillar 22 of the `lean-agile-agentic` guide ("Lean Workflow: Issues to Roadmap"), which proposes that PRDs, FRDs, NFRDs and specs live in an issue manager rather than as repo files, and defines what makes an issue agent-ready.

The first draft was written against the guide's *published* build, which still served an older, absolute claim ("don't commit a PRD to the repo"). The guide's repository source at revision `23d61db` had already softened it to "one canonical, reviewable plan; a tracker is a default, not the only option". Anything written from a published static site in this family needs to be checked against the source repo, because the two drift.

## Why the structure is what it is

**Five templates, not one.** The guide names ISSUE as the baseline for PRD, FRD, NFRD, spec and bug. Collapsing them into one template loses the thing that makes each useful: a PRD needs `Splits into`, an NFRD needs a threshold and the gate that enforces it, a bug needs a reproduction. They differ in required sections, so they are different files.

**Templates live in `templates/`, not inline in `SKILL.md`.** Progressive disclosure: an agent filing a bug should not carry four unused templates in context. The cost is that `skills/*/templates/**` needed a lint exemption (see below).

**Size as bands, not as prose.** The first draft defined `M` as "the largest change one session can build and one reviewer can read carefully". That is circular, and it contradicted the skill's own rule that an uncheckable criterion is a design question. The numbers come from the guide's trunk-based pillar, which gives "about 150 changed lines, one slice. Over 400: split first". They are a budget borrowed from the source, not measured here — that is why the skill says a project's own size gate overrides them.

**Size has two phases.** The templates originally said size was "Confirmed by the plan's file list", but at filing time no plan exists — in the guide, the plan is written by the implementing agent at pickup. The estimate and the confirmation are different claims made at different times by different actors, so the skill and the templates now say which is which. This was the subtlest defect in the first draft: a forward reference that looked like evidence.

**Two gates, because one number was making two different predictions.** "One session" and "one careful review" are not the same constraint, and changed lines only predicts the second one. A session's cost is dominated by exploration — files read to locate the change, call sites verified, test-fix cycles — so a 30-line fix across eight call sites in unfamiliar code is a bigger session than a 300-line new file nothing calls. The two axes invert on two common classes: mechanical bulk (large in lines, cheap both ways) and dense logic (small in lines, expensive both ways). The skill already had the session-axis instrument and was not using it as one — the pickup plan enumerates exactly files touched, interfaces changed and unknowns. So the rule is now explicit: lines is the reviewer gate, the plan's contents are the session gate, the band is the lower of the two.

**The line-counting rule is written down because it swallows a whole band.** An issue with 150 lines of implementation and 150 lines of criteria-named tests is `M` under one counting rule and `S` under another. The rule chosen — added and modified hand-written source and test lines, generated and vendored output excluded, pure deletions at zero — matters less than it being stated, because without a denominator the bands cannot be measured later.

**The 50-line boundary was dropped.** `XS` and `S` changed no decision in this system: both fit one session, both fit one review, both file identically, both get one PR. A boundary that changes no decision is overhead that will absorb argument at filing time for nothing. `XS` survives as a shape band with no number (one file, one criterion, no interface change), which keeps the useful "this is trivial" signal. The remaining boundaries are the two that change a decision: the ~150 target and the 400 ceiling.

**Target and ceiling, not four permitted zones.** The upstream source said "expected about 150, over 400 split" — a target plus a hard stop. The first draft's table flattened that into four bands reading up to 400, and a ceiling reads as permission: plans drift to fill whatever band they were handed. Restoring "target ~150" inside the `M` row costs one clause and keeps the calibration the source had.

**The pickup agent states its size before reading the filed one.** The agent receives the band as part of the issue, then produces the plan that gets checked against it — and a plan is trivially cheap to make fit: narrow the file list, defer two edge cases into "deliberately not doing", name three tests instead of six. Band-driven narrowing and honest scoping produce an identical artifact, so the check could not fail by construction.

Be honest about how much the sequencing fix buys. An agent reading one issue body sees the filed band whatever order the sections are in, so this is an obligation and an audit trail, not a mechanism — the `## Picking this up` section sits above `## Size` to make the obligation the first thing read, which is the most a single document can do. What it actually produces is two stated numbers instead of one, which is what the anchoring test in the measurement plan needs; without it there is nothing to compare. Preventing anchoring would take a second actor or a PR-time check, and the latter is out of scope for a filing skill.

**`unknown` is a valid band.** The vocabulary `<XS | S | M>` forced a number onto surface nobody had read, which is the same false precision the skill condemns everywhere else ("a criterion you cannot state mechanically is a design question"). `unknown — the pickup plan sets it`, plus a line naming what is not known, is the honest filing when the codebase has not been looked at.

**The `L` rule needed exemptions.** "Over 400 is not a spec, file it as a PRD" conflated size with decomposability. Several legitimately atomic changes are large in lines and trivial to review: a codemod or rename across call sites, a net deletion, a new isolated file with no callers, generated or declarative bulk, and a contract change that cannot land in parts without breaking the trunk. Forcing those into a PRD with child specs is overhead at best and a worse decomposition at worst — a half-renamed codebase, a half-implemented class, a broken intermediate trunk state. The exemption list also doubles as an instrument: if more than roughly one issue in four claims one, the lines gate is measuring the wrong thing.

**Project is the default parent; milestone is optional.** The source's tree is explicit: milestone is marked "Optional", project is "the parent of every issue". The first draft made all three levels optional and allowed `none` at any of them, which inverted the one structural invariant in the model. The compromise in the current text: project is the default parent, omitted only when the tracker already gives the issue a home (GitHub does, via the repo) *and* the work is a single issue.

**The roadmap level is honest about GitHub.** A GitHub "roadmap" is a view configuration on a Project, created in the web UI. No `gh` command produces one. The skill proposes the roadmap and labels it a manual step rather than pretending to create it. Linear initiatives are creatable, so the skill distinguishes them.

## Design decisions worth knowing

- **Creation order is load-bearing.** Labels and milestones before issues, because `gh issue create --milestone` needs the milestone to exist; project after issues, because `gh project item-add` needs issue URLs. The first draft created issues first, which silently required an unspecified `gh issue edit` pass.
- **Tracker-neutral contract, one verified implementation.** Steps 3 and 9 say what must be read and created in concept terms, then give `gh` as the worked example. Writing Linear and Jira command sets as well would triple the verification burden — and the one set that existed already contained a command that does not exist. More to the point, MCP tool signatures vary per server, so writing them would mean inventing operational instructions, which is exactly what the authoring standard forbids. An agent with a Linear MCP gets the contract and its own tool list, which is enough; an agent with no tracker is told to stop.
- **`gh milestone` does not exist.** Milestones are created through `gh api --method POST repos/{owner}/{repo}/milestones`. This is the kind of thing that only surfaces by running `--help` against the installed CLI, and it was load-bearing: the skill ordered milestones before issues and gave no command, so an agent would have guessed `gh milestone create` and improvised past the failure.
- **Create issues in dependency order; the rewrite pass is the fallback.** The first draft made the rewrite pass the primary path: file with blockers named in words, then edit each body once the numbers exist. The 2026-10-09 tracker run never needed it, because it filed blockers first and every `Blocked by` could name a real number as it was written. That is strictly better — one write per issue instead of two, and no window in which the tracker holds a dependency nothing can follow. The pass survives only for what ordering cannot fix: a cycle, or a blocker filed in a different session.
- **The scratch file is kept on partial failure.** Deleting it after a half-finished creation sequence destroys the only record of what was supposed to exist. It is deleted only when every object in the proposal has been confirmed.
- **The proposal file lives outside the repo.** The first draft said "the scratchpad" with no path at all, which an agent resolved by creating `.scratch/` in the working tree *and editing `.gitignore`* to cover it — observed in the 2026-10-08 eval, on this vault's own repo. A filing skill has no business writing to a tracked file, and `.gitignore` is tracked. The path is now `${TMPDIR:-/tmp}/issues-<date>.md`, reported back so a human can find it, with nothing to clean up in the repo afterwards.
- **Impact label, not just kind label.** The guide's PR-review pillar sets review rounds and maximum agent autonomy per impact label. If the issue is the agent's entry point, a kind label alone does not gate autonomy, so step 9 creates the project's impact label too.
- **Dedup matches on the outcome line.** Title similarity produces false positives (two issues about the same file, different behaviour) and false negatives (the same outcome worded differently). Outcome matching is still judgment, so the skill is told to ask when it cannot tell, naming the candidate.
- **"Agent-complete is not done" is on the template, not only in the procedure.** A rule that exists in the skill but not in the issue body is a rule the implementing session never sees. Hence `## Closed by` on `spec.md` and `bug.md`.

## What was deliberately left out

- **No status transitions.** The skill files issues and stops. Moving an issue to review belongs to the session that implements it, and closing belongs to a human or a gate.
## Trigger narrowed to the execution-setup moment (2026-10-27, owner instruction)

> "issues-to-roadmap should be invoked only when we have a full plan to create and start working, so we can document each piece of it by the type of file and log all the interaction, progress, context that a reader and agent needs to keep up with the status."

The description previously claimed any "break work down" request and any pasted notes or transcript. It now requires that **the plan is settled and work is about to begin**, and it explicitly rejects breaking down notes whose decisions are not settled.

Why this was the right narrowing, beyond it being an instruction: the old description was winning activation on tasks it was not the best artifact for. Measured in the router's round-1 to round-3 evals, it took three runs of a task whose correct answer was arguably `playbooks/issue-to-ready-specs/`, purely because its description claimed "break work down" and that playbook's did not. Trigger breadth was buying it work it should have declined.

**Two consequences, both since resolved by the owner (2026-10-27):**

1. **Exploratory breakdown has no owner, and that is intended.** "Here are my notes, break this into issues" previously landed here. It no longer matches this skill, it has never matched any playbook (the vault's playbooks run issue → specs, the opposite direction), and `playbooks/issue-to-ready-specs/` requires an existing tracked issue. **Owner decision: leave it uncovered.** Unsettled work wants a human decision before it becomes a backlog, which is this skill's own "an open question stays an open question" rule applied one level up. `ai-stuff-artifact-router` declines that shape with no pointer and says the decisions need settling first.

   Observed behaviour once, the same day, unprompted and without this skill activating: asked to file issues from a session where "nothing is really decided" and two people disagreed on scope, the session refused and explained why — *"writing issues now would freeze an open disagreement into the tracker as if settled… Issues created on top of it get silently reinterpreted by whoever picks them up."* It recommended closing scope first, then a plan document, then issues. That is the intended outcome of leaving the shape uncovered.

2. **The log is the tracker, and this skill sets it up. Nothing to build.** The instruction's second half — "log all the interaction, progress, context that a reader and agent needs to keep up with the status" — reads as the *purpose* the tracker serves, not a new capability for this skill. **Owner decision: the tracker is that log.** The issues, their comments and their state hold it; this skill creates the structure that makes it followable, which is what "document each piece of it by the type of file" already does via the five kinds.

   So `SKILL.md`'s closing boundary stands unchanged and is not in tension with the instruction: *"This skill files issues; it does not move status, and it does not claim an issue is ready because it exists."* Writing and maintaining a separate running log remains out of scope. If that is ever wanted, it starts as an experiment rather than an edit here.

- **No repo writes at all.** It creates and edits nothing under the project repo, including `.gitignore`. The proposal goes to a temp path outside the tree. Spec documents are the job of `playbooks/issue-to-ready-specs/`.
- **No estimation beyond the bands.** No points, no hours, no cycle time. Those invite gaming and test none of the model's actual claims.
- **No Jira specifics.** The templates assume a free-form markdown body. Jira's required custom fields would need a separate mapping, and nobody has needed it yet.
- **No vault-level policy about where a spec lives.** The rule the skill needs — one canonical home, link rather than restate — is stated in the skill itself, in two lines. A separate standards file would be a second copy of a rule whose entire point is that copies drift.
- **No PR-time size enforcement.** The forecasting review's strongest unaddressed point: all pressure against an underestimate sits at filing, the least-informed step, and the only check after it is a plan the implementing agent grades itself. A terminal rule ("at PR open, a diff more than ~50% over its band routes to split-or-justify before review starts") would be the one control that actually prevents the worst failure. It does not belong here — a filing skill has no PR-time hook — and it is the project's size gate's job. Recorded as a boundary in the README rather than quietly dropped.
- **Flag removal is unsized.** "An unfinished slice ships behind a feature flag" treats flags as free. Removing one is real deferred work that nothing in this model sizes or owns; small per instance, compounding across a roadmap.

## Maintenance notes

- **Re-verify against the guide source, not the published site.** The guide repo's `content/pillars/22-tracker.mdx` and `content/details/22-tracker.mdx`. The README pins revision `23d61db`. If the pillar's storage claim or the agent-ready rules move, this skill and `skills/lean-agentic-baseline/references/tier-3-scale.md` both need the same edit — two files, checked together, because they are two readings of one pillar.
- **Test the approval gate by not mentioning it.** Rounds 1 and 2 told every session not to create anything, for eval safety, which meant the skill's own restraint was asserted for two whole rounds and measured in neither. The only way to test it is a sandbox tracker you do not mind polluting and a prompt that says nothing about stopping. It passed, but that was unknown until round 3.
- **`evals/` holds all three rounds.** `plan.md` has the assertions, written before any run; `results.md` has round 1 (2026-10-08, 14.5/18, one missed activation), round 2 (31/31, 3/3 activation after four fixes) and round 3 (the creation sequence, end to end on a real private tracker). What is left: failure injection on step 9 — partial-failure resume and a missing `project` scope mid-sequence; the `prd`, `frd` and `bug` kinds in creation; and a fourth prompt in the sequencing shape, since P3 is still n=1.
- **Re-run the behaviour checks after any substantive body edit.** The authoring standard requires it and round 2 is why: four edits between rounds, and three of them changed measured behaviour. An edit that looks like wording often is not.
- **Install it where the harness looks, not by injecting a path.** Discovery testing only works if the harness decides. The project-level convention here is a symlink in `.opencode/skills/`, which is how `ai-stuff-artifact-router` is wired; `ln -s ../../skills/issues-to-roadmap .opencode/skills/issues-to-roadmap` is enough, and the orchestrating session's own skill list picks it up without a restart. Telling a session to read a path tests behaviour, not activation.
- **The level vocabulary needed an example, not a better rule.** Both round-1 runs got step 7 wrong in different directions — a quarterly goal filed as `Roadmap: none`, and "getting checkout live" filed as a milestone where project is the default parent. The rule was already stated correctly and prose restating it would not have helped. A five-line worked tree fixed both in round 2, which is the authoring standard's point about preferring examples for exact usage. Reach for an example first the next time a step is misread.
- **Six fields confirm or kill the size bands.** All of them are recorded at points that already exist, so measuring costs nothing extra: `size_filed`; `size_planned` (the band the pickup plan implies, **written before the filed band is read** — without that ordering the anchoring test is impossible); `lines_actual` at PR open under the skill's counting rule; `split_at_pickup`; `review_outcome` (did review request changes on correctness, not style, and did a defect surface afterwards); and `completed_in_one_pass` for the session axis. Twenty to thirty issues is enough, and ten shows whether the spread is wild — these are strong claims and strong claims die fast. What the results would mean:
  - *reviewer axis wrong*: `lines_actual` is uncorrelated with correctness outcomes — big PRs review clean, small ones carry the problems. Move the reviewer gate to files touched and interfaces changed.
  - *session axis wrong*: `completed_in_one_pass = no` tracks file count but not lines. Then the lines table governs review only, explicitly.
  - *filing estimates worthless*: `size_filed` agrees with `size_planned` no better than chance. Then drop filing estimates and let the plan be the only instrument — it already costs nothing extra.
  - *anchoring confirmed*: `size_planned` matches `size_filed` at a high rate while `lines_actual` overshoots far more often than it undershoots. Plans agreeing with estimates while reality disagrees with both is the signature.
  - *400 too high*: PRs in the 250–400 range get fast approval with no correctness comments while smaller ones draw substantive ones. A suspiciously clean review of a big diff is more likely inattention than quality.
  - *XS redundant*: no issue in the sample was handled differently for being `XS` rather than `S`. Merge them.
- **A local prior is available before any run.** `git log --numstat` across repos already shipped, bucketed by diff size against whether those PRs needed follow-up fixes, replaces the borrowed reviewer-axis distribution with a measured one. It says nothing about the session axis (not agent-authored), but it is an afternoon's work and it is the difference between "borrowed from a citation chain" and "measured here".
- **Re-verify the `gh` commands against the installed CLI, not from memory.** Verified at `gh` 2.87.3. `gh milestone` has never existed; `gh project create --title` and `gh project item-add --url` do. Run `--help` on each before trusting a flag, and re-run after a major `gh` bump.
- **`skills/*/templates/**` is exempt from frontmatter lint** via a generalized rule in `scripts/doc_lint.py`, which replaced three hardcoded `skills/prompt-factory/templates` paths. If a new artifact needs a different asset subdirectory, extend that rule rather than adding another hardcoded path.
- **Lifecycle note.** `skills/README.md` says a skill lands in `skills/` only once validated, with drafts in `experiments/`. This skill is `draft` and lives here, matching the existing precedent of `skill-authoring` and `liteparse`, which are also `draft` in `skills/`. The index's claim and the directory's contents disagree; that is a pre-existing inconsistency in the vault, not a decision made for this skill.

## Known gaps

- No measured run, and no without-skill baseline.
- **No discovery test.** The authoring standard wants should-trigger and should-not-trigger prompts run separately, and this skill has a real false-activation surface: "issues" is a word that turns up in "I'm having issues with X". The description names the trackers and the three negative boundaries to narrow it, but narrowing by wording is not evidence that the harness activates correctly.
- No Linear or Jira path exercised. The `gh` commands are verified against the installed CLI's help but have not been run against a repo, and no MCP equivalent has been written.
- Nothing verifies "link, don't duplicate" — an agent can still restate in an issue body criteria that already live in a reviewed repo document. The check is human, at review.
- The dedup step reads at most 200 issues. A busier repo needs search rather than a list.
- **Installation does not carry `templates/` automatically.** Step 6 now names the six files as a required dependency and tells the skill to stop and say which is missing rather than invent a shape, so a bad install fails loudly instead of silently. What it still cannot do is install them — any path that copies only `SKILL.md` produces a skill that stops on first use.

## Carrying the whole plan in the tracker (2026-10-31)

Source: a dry run on a large platform redesign. The input was a plan of several sections — architecture corrections, audits, contracts, migration steps, a decision log — longer than GitHub's 65,536-character issue-body limit, plus HTML planning pages, a design-export archive and prototype pages of several hundred kilobytes. The draft came to a few dozen issues across several milestones, and the owner then decided the plan must live in the issues rather than in a linked repo file. That decision is what exposed the gaps: the skill had been written for the case where design lives in a reviewed document the issues link to, and had nothing for the case where the tracker is the only home. A smaller feature filed with the skill earlier had put its design in the PRD body as numbered sections that specs cited; that worked at its size and is where the `D` ids come from.

The principles were kept unchanged: one canonical home, one issue per decision, mechanical criteria, draft-show-stop, open questions never become issues. Every change below is in the text only. Round 4 in `evals/plan.md` has an assertion for each; none has been run (owner decision, 2026-10-31: write the evals, leave them unrun).

1. **No home for design content → a `design` kind, and a PRD `## Design` section.** Decisions, contracts, audits and migration steps are not work items, so none of the five kinds fit, and the earlier run had improvised a PRD section. Both shapes are kept because both are right at different sizes: a section when one PRD owns the design and it fits, its own issue when several PRDs cite it or it would overflow the body. The deciding rule is mechanical so the choice is not taste. Ids are stable and never reused because specs cite them by number; renumbering would silently repoint every citation.
2. **Body limits → measure, split by area.** GitHub caps a body at 65,536 characters and the plan was longer, so "put it in the issue" was impossible as stated. The skill now measures each body with `wc -m` before showing the proposal and splits at ~60,000, leaving room for later edits (an `Answered` line added later should not push a body over). Splitting by area rather than by length keeps each part readable on its own, and never splitting inside a D entry keeps citations whole. Linear and Jira limits were deliberately not written in: they were not verified here, and the authoring standard forbids an unverified number. The agent is told to look them up.
3. **Non-text artifacts → pinned links under `## Artifacts`.** HTML pages, an archive and large prototypes cannot live in a body, and GitHub's API cannot upload attachments. The only links that never move are a commit permalink and a release asset; a branch link silently changes under the reader. This keeps the skill's "no repo writes" rule: committing an artifact is named as a prerequisite in a new `Before filing` section for a human or another session, not done by the skill.
4. **Answered questions → an `Answered` record.** The skill forbade closing open questions itself but had nowhere to put a human's answer, so the answer and its reason were lost once the chat ended. The record is fixed in place (beside `Still open` in the PRD and design templates) and carries who decided, when and where, so a later reader can tell an owner's decision from an agent's assumption. The skill records only answers a human gave; an inferred answer is still open.
5. **Provisional thresholds → a provisional NFRD form.** The owner's "measure a baseline first, then set the limit" was a legitimate decision the template could not express; an agent would either invent a number or leave the requirement unfileable. The form keeps every part checkable: the number in force now, the spec that measures the baseline, and the trigger to re-decide. The NFRD stays open until the threshold is final, so a provisional number cannot quietly become permanent.
6. **Deliberate stubs → a stub pattern and a `Stubbed on purpose` section.** A surface shipped as a visible "not built yet" placeholder is work (something renders) plus a promise (a PRD later), and `Left out on purpose` lost both. The stub's criterion goes in the spec that renders it, and the real surface gets a PRD whose `Splits into` says it is not yet planned, so the promise is tracked and findable.
7. **Delivery mode → stated once, with what review and closing mean in each.** The owner chose one PR per milestone, opened only after a full local build was tested. The sizing rule ("one issue, one session") does not change, because it is about how much one session can do, not how work reaches review. What changes is the meaning of "moved to review" and "Closed by", so the table defines them per mode, and every spec and bug carries the mode. Issue comments are named as the progress channel because the tracker is the log (owner decision, 2026-10-27).
8. **Handoff → the drafting session files, or a `roadmap-proposal` issue.** The proposal must stay out of the repo, so only the session that wrote it could find it. Two options were considered: post the proposal to the tracker, or ask the human to move the file. Posting won because it needs no repo write and a fresh session can find it; it is offered, not default, and only on the human's say-so, so draft-show-stop holds — the approval is of posting it.
9. **Reads without `gh` → stop and name the missing reads.** In an MCP-only session milestones and projects could not be listed, so the read was partial, and the skill gave no fallback and no rule for what to do next. Writing per-server MCP commands was rejected for the same reason as before (signatures vary; inventing them is the forbidden failure). Instead the required reads are a checklist, each either done or named missing, and nothing that could duplicate an unseen object is proposed without the human's confirmation.
10. **House conventions → read them, adopt them, write them down.** The best evidence of how the team files was an earlier run of this skill (title prefixes, an area label, milestone names, issue types, sub-issues). Step 3 now looks for that and records it on a `House conventions` line, so a reviewer sees what was copied rather than wondering why titles look the way they do. A convention that breaks the skill's rules is named, not copied. Sub-issues and issue types are used when the repo has them; `gh` 2.89 has no flag for either, so the REST calls are given and marked unrun.

Two failure paths from the round-3 test notes were specified at the same time:

- **Resume after a partial creation failure → the proposal file is a ledger.** The old text said "resume from the first missing object" without saying how to know which one that was. A create can succeed after its response is lost, so trusting the session's memory risks a duplicate. Now each object is marked `created #n` as it exists, and a resume re-reads the tracker and matches unmarked objects by title and outcome before creating anything.
- **Missing `project` scope → known before filing, reported if hit mid-sequence.** The scope is checked in step 3 and stated on the proposal, so the human sees that the project level will be skipped and how to restore it. If it still fails at step 9.4, everything before it exists (labels, milestones and issues need only repo access), so the project and its item-adds are reported as the missing objects and the run resumes from there after `gh auth refresh -s project`.

### Re-running at full scale

Give a fresh session a plan at the scale that found these gaps, with its artifacts, the skill installed and not named, and ask for a draft only. Pass: the design content becomes design issues split by area, each body measured under ~60,000 characters; specs cite `#n D<k>`; non-text artifacts appear as pinned links, with any not yet committed listed under `Before filing`; baseline-first NFRDs use the provisional form; stubbed surfaces appear under `Stubbed on purpose`; the header states the delivery mode the owner chose; conventions from any earlier filing are on the `House conventions` line. The round-4 assertions in `evals/plan.md` grade the output.
