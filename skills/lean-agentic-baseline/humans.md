# humans.md — lean-agentic-baseline

## Origin

Built in one session from a single source: `lean-agentic-baseline.html`, a downloaded field guide (v3.2) the user had saved locally. The guide is a long single-page HTML document (~219KB, no build tooling, just a static page) structured as 25 "pillars" grouped into 4 tiers, each pillar following the same shape: an "In brief" one-liner, a "why" section, one or more copy-ready code/config templates, and a "Sources" list citing where each claim comes from (or explicitly flagging it as the guide's own proposal).

Extraction method: fetched the HTML, stripped script/style tags, collapsed markup to plain text with `python3` + `re`, then read it sequentially in ~700-line chunks via the Read tool to build a complete map before writing anything (25 pillar headings found via `grep -n "^In brief$"` first, to confirm full coverage before starting synthesis).

## Why this structure

Followed this vault's own `skill-authoring` process and `docs/standards/artifact-structure.md` three-file convention, with one addition specific to this skill's shape: a `references/tier-N-*.md` split rather than one flat `references/` file per concern, because the source material is *already* organized by tier and each tier reads as a coherent unit (Tier 0 is "day one," Tier 3 is "don't adopt before Tier 0/1 are green" — collapsing tiers into topic-based files would have broken that sequencing signal).

`scripts/checks/` (plural, one script per mechanically-checkable pillar) mirrors the source guide's own script blocks almost verbatim — these are largely transcriptions of the guide's own bash, not new inventions. The one thing this skill adds that the source guide doesn't ship as a single artifact: `scripts/scorecard.sh`, which runs presence-detection across all 25 pillars in one pass and reports the four-outcome model (`PASS`/`FAIL`/`SKIP`/`UNVERIFIABLE`) that the guide *describes* in prose ("Meta Framework & Drift Checks" pillar) but doesn't ship as working code. That synthesis — turning the guide's four-outcome idea into an actual script that implements it across every pillar — is the main value-add of this skill over just reading the guide.

## Historical design decisions (superseded where noted below)

**Why a presence-and-consistency scorecard, not a "how good is this repo" scorer.** The source guide is explicit that "a green report is not safe" (verbatim quote, Tier 0 · Permissions section) — several controls (branch protection, token scope, egress policy, secrets on disk) cannot be seen from repo contents at all. Rather than either (a) ignoring this and producing a falsely reassuring single score, or (b) trying to fake-verify unverifiable things via heuristics, `scorecard.sh` reports those rows as `UNVERIFIABLE` explicitly and never silently omits them. This was a deliberate choice to preserve the source guide's own epistemic honesty rather than "improving" it into a simpler pass/fail that would misrepresent what was actually checked.

**Why check scripts are copied near-verbatim from the source rather than rewritten.** The source guide's bash was already tested by its own author against real conditions it describes evidence for (e.g. Run 4 in `change-impact-diagram`'s own evidence log shows this vault's convention of verifying scripts against real repos, not just reading them for plausibility — same standard applied here). Rewriting them "more elegantly" would have introduced untested behavior for no benefit; the value is in assembling them into one discoverable, tested package, not in improving bash that already works.

**Why `scorecard.sh` uses filename/config heuristics instead of actually running each tool.** Actually running `depcruise`, `lint-imports`, `golangci-lint`, etc. would require installing them, which the scorecard (deliberately read-only, zero side effects) shouldn't do. Presence-of-config is a reasonable proxy for "this pillar has been set up" even though it can't confirm the tool actually passes — that's a known, stated limitation (see README.md's Failure Modes), not an oversight.

**Why diff-scoped checks (`no-ticket-refs.sh`, `no-test-weakening.sh`) are separate from the scorecard's main loop.** They need a real base-ref diff to operate on; running them against an empty/absent diff would produce a meaningless PASS. The scorecard notes their *mechanism's* presence (does CI exist? does the script exist?) as its own row, but doesn't fake-run them. This is called out explicitly in SKILL.md so a future agent doesn't "fix" it by trying to force these into the main scorecard loop.

## Maintenance notes

- If the source guide is updated (it's versioned, v3.2 as of this session, "Working draft"), the fastest way to find what changed is `grep -n "^In brief$"` on a freshly-extracted text version — that pattern anchors on all 25 pillar intros and made full-coverage verification cheap during authoring. Diff pillar count and titles before doing a deeper diff.
- The guide's own dated caveat: "Every link was opened and checked when it was added: 18 September 2026 for the original set, 20 September for the entries added since." Vendor docs (especially Claude Code's own) move fast — if a user reports a `references/` claim is stale, check it against current Anthropic docs before trusting either this skill or the original guide.
- `scripts/scorecard.sh`'s stack-detection heuristics (boundary linter, validate entrypoint, etc.) are scoped to what the source guide documents: TS/JS, Python, Go, JVM, Rust in a couple of places. A repo using a different stack (Elixir, Ruby, PHP, etc.) will read mostly `SKIP` — this is a known gap, not a bug, and extending it means adding rows to `scorecard.sh`'s per-pillar detection logic, ideally after checking what config file names those ecosystems' equivalent tools actually use (don't guess).
- The templates directory (`assets/templates/tier-{0,1,2,3}/`) intentionally keeps the source guide's placeholder values (pnpm, `your-org`, `src/api → src/services → src/repos`). Resist the urge to "genericize" further — the guide's own examples are already a deliberately simple running example, and stripping them to pure placeholders (`{{PACKAGE_MANAGER}}`) would make the templates harder to read as working examples, contrary to the "show code, not prose" principle this vault's `skill-authoring` process itself teaches.

## Version pinning (added after initial authoring)

The user asked, after the first version of this skill shipped, for the skill to "consider the version of the document it will enforce" and "keep a local file when it's run to be aware of the files that are created to keep their version pinned in case of future improvements on the original source guide." Two distinct problems were hiding in that one sentence, and both needed solving:

1. **The skill itself needs to know what guide version it's currently built from**, so it can tell a user "you're looking at v3.2 output" instead of silently presenting content as if the guide never changes. Solved with `VERSION.json` at the skill root — a single source of truth, regenerated only by `scripts/generate-version-manifest.sh`, never hand-edited (hand-editing a hash file defeats the point of hashing).
2. **A *target repo* that adopted a template needs a record of what it adopted and when**, so that when the skill's guide version bumps later, that repo can be told "your AGENTS.md is pinned to the v3.2 template, which has since changed" instead of either (a) never knowing, or (b) some future run silently overwriting a file the team may have already customized. Solved with `scripts/adopt.sh` (writes a manifest *into the target repo*, not into the skill) and `scripts/check-pinned-versions.sh` (reads both manifests and diffs hashes).

**Why the manifest lives in the target repo (`.lean-agentic-baseline/manifest.json`), not in the skill.** The skill is a shared, reusable artifact — one skill directory, potentially adopted by many target repos, each adopting different templates at different times. State about "what did *this* repo adopt" cannot live inside the skill without either (a) the skill accumulating unbounded per-target-repo state, or (b) different target repos clobbering each other's records. Putting the manifest in the target repo mirrors how `.git/`, `lockfile`, and `docs/decisions/INDEX.md` all work in this same guide — state about a specific repo's history lives in that repo.

**Why hashes, not just a version string.** A guide-version bump doesn't guarantee every template changed — some pillars might be untouched between v3.2 and v3.3. Recording a hash per file (not just "adopted at v3.2") means `check-pinned-versions.sh` can report `PASS` for files whose template didn't move even after a version bump, instead of flagging everything as stale just because *some* pillar changed. This was a deliberate choice to keep `DRIFT` a precise, actionable signal rather than a blunt "the guide updated, re-check everything" alarm — the same "don't cry wolf" reasoning the source guide itself uses for bot review rounds (a visual-diff round that blocks on any difference gets muted within a week).

**Why archive `VERSION.json` on version bump instead of just overwriting it.** Directly mirrors the guide's own ADR rule: "append-only... status transitions are the only edits... so the reasoning history survives." Losing the old `VERSION.json` would mean losing the ability to answer "what did v3.2's AGENTS.md template actually look like" for any repo still pinned to it. `references/version-history/<old-version>.json` is the same pattern this vault's own `docs/decisions/` uses, applied to a skill's own version manifest.

**Why `adopt.sh` refuses to record a template not present in `VERSION.json`.** This is a deliberate hard-fail, not a warning. If it silently recorded an unknown template path, `check-pinned-versions.sh` would later look up that path in `.files` and find nothing to compare against — degrading to a silent no-op instead of a clear signal. Failing loudly at adoption time is cheaper than debugging a manifest entry that quietly never gets checked.

**What was deliberately left out of this pass:** a way to *auto-apply* a `DRIFT` update (re-copy the new template over the target repo's file). This was considered and rejected — the whole reason `EDITED` exists as a distinct outcome from `DRIFT` is that a target repo may have customized the adopted file on purpose, and an auto-apply would need to disambiguate "safe to overwrite" from "someone's customization" without enough information to do so reliably. Leaving the human in the loop for that decision is consistent with the source guide's own "ask first" tier for anything that touches a repo's committed conventions.

## Original validation gaps

- Never run against a real application repo with a real `package.json`, real ADRs, and a working CI pipeline end-to-end — only against this docs-only vault (adequate for testing the Tier 0/onboarding detection paths, useless for testing Tier 1's boundary-linter or devcontainer detection) and a synthetic scratch repo (adequate for testing the ADR-drift failure path). Before promoting this skill's status further, run it against a real, structurally different codebase and record the result in README.md's Evidence section.
- No test yet of the "implementing a pillar" workflow end-to-end (SKILL.md § Implementing a pillar) — only the scoring workflow has been exercised. An agent following that section to actually copy a template into a target repo and wire in a check has not been observed.
- `scorecard.sh`'s Tier 3 detection is the thinnest (mostly file-presence checks for labeler/deploy/drift workflows) since Tier 3 pillars lean hardest on platform-level configuration (required reviewers, branch protection) that's `UNVERIFIABLE` by design — there isn't much more presence-detection to add here without overreaching into false confidence.
- The version-pinning workflow (`adopt.sh` / `check-pinned-versions.sh`) has been tested against a synthetic scratch repo with one adopted file, exercising all four outcomes (PASS/DRIFT/EDITED/GONE) plus both SKIP paths (no manifest, unknown template). It has not been used across a realistic multi-file adoption (a repo that adopted 10+ templates over time, some customized, some untouched) — the manifest format (a flat `adopted` array) should scale fine, but hasn't been exercised at that size.
- `scripts/generate-version-manifest.sh` requires editing four bash constants by hand (`GUIDE_TITLE`, `GUIDE_VERSION`, `GUIDE_ASSESSED_DATE`, `SOURCE_FILE`) rather than taking them as arguments or reading them from a metadata block in the source HTML. This was a deliberate simplicity choice for a script that runs rarely (only on a guide version bump, by a maintainer, not by an end-user session) — reconsider if this skill starts tracking multiple source guides instead of one.

## 2026-10-06 refinement

Static inventory cannot emit VERIFIED; empty directories, empty configuration examples and a known no-op validate no longer earn reassuring passes. Missing detection does not mean inapplicable.

Introduced a context/feasibility/ownership/acceptance/outcome assessment matrix. Its tests and measures are proposals; fixture success does not establish real-team benefit. Human owners control independent authority, while authorized APIs and safe probes can reduce manual checking.

Adoption now records both upstream and adapted-file hashes; combined upstream/local changes remain visible. Legacy records without an adaptation baseline remain unknown rather than being guessed. Paths are contained, target existence and source hashes checked, malformed manifests rejected, and JSON writes atomic. Immutable content snapshots now permit actual diffs; the original claim that hashes alone could recover old content was incorrect.

Version metadata separates original v3.2 template provenance from this skill revision and the guide source revision reviewed for coverage. Do not retag old examples as newly extracted or vendor-verified. Python 3.10+ replaces the previous jq requirement; this is an explicit portability tradeoff for structured validation and regression tests.
